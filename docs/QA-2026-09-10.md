# Correctif du transport Cloudflare — 10 septembre 2026

## Défaut reproduit

Le moteur installé (`workerd 1.20260828.1`, via Miniflare) lève une TypeError pour
`new Request(url, { redirect: 'error' })`. Le connecteur Supabase utilisait cette
option et transformait l’erreur en `upstream_unreachable`, puis `data_unavailable`.
Cela arrive avant le départ de la requête, même si `curl` vers Auth et REST réussit.
Le connecteur LLM contenait le même défaut. Les tests précédents, exécutés dans
Node avec fetch simulé, ne pouvaient pas le détecter.

## Correction

Les deux connecteurs utilisent `redirect: 'manual'`, puis rejettent toute réponse
3xx et annulent son corps. Aucune redirection ne peut propager les clés ou les
jetons vers une autre destination. Les délais, limites JSON, contrôles de rôles
et restrictions de budget sont conservés.

## Validation

Résultats locaux du 10 septembre : `npm test` **124/124**, dont les six tests
workerd ci-dessous ; `npm run test:starter` **7/7** sur le build final ;
`npm run typecheck`, `npm run lint:app` et compilation de production réussis.

Six tests d’intégration dans le vrai moteur workerd, avec services distants simulés :

1. `/health` atteint Auth et PostgREST et retourne HTTP 200 ;
2. référence/code, refus d’un mauvais code, cookie HttpOnly, lecture et fermeture ;
3. connexion administrateur limitée au préaccès MFA, sans jeton dans le JSON ;
4. redirection Supabase refusée sans second appel vers sa destination ;
5. boucle Gemini avec consultation du dossier autorisé et réponse ;
6. redirection Gemini refusée et repli explicitement identifié.

Ces tests utilisent la base D1 locale et les handlers applicatifs, sans remplacer
fetch dans le Worker. Les seuls éléments simulés sont les services distants.
Ils sont inclus dans `npm test`, donc également dans les contrôles GitHub.
Miniflare, déjà présent via Cloudflare, est déclaré explicitement avec la même
version verrouillée ; aucun changement de version des dépendances existantes.

## Contrôle Supabase et limites

L’organisation fictive reste active et les quatre migrations du dépôt sont
alignées avec le projet distant. Le conseiller de sécurité signale trois tables
avec RLS sans politique publique (`case_access_codes`, `case_commands`,
`case_sessions`) : elles restent volontairement réservées au serveur.

Il signale aussi la protection contre les mots de passe compromis désactivée.
Cette option demande le forfait Pro ou supérieur selon la
[documentation Supabase](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
Aucun forfait payant n’a été activé ; la seconde vérification TOTP obligatoire
pour les administrateurs est conservée. Cet avertissement n’est pas lié à
l’erreur de transport corrigée ici.

Les essais n’envoient aucun email, n’utilisent aucune clé privée et ne déclenchent
aucune consommation de LLM. Le runtime local de cet environnement ne résout pas
le domaine Supabase : l’essai HTTP externe reste à refaire dans le Codespace du
propriétaire. Ses réponses Auth/REST 200 constituent un contrôle distinct.

Il reste à tester ses identifiants/TOTP et sa clé Gemini dans son environnement.
Ce correctif ne crée pas de parcours d’acceptation d’invitation email et ne
constitue pas une certification générale de production.
